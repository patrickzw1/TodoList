# Prototype Instructions

For UI implementation or browser acceptance that needs a preview, run/reuse the project server and open it in an available browser. Pure document reviews do not require starting a server.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## TodoList product decisions

- The main review task remains read-only and owns issue collation and acceptance. Implementation and fixes belong in the dedicated TodoList development task, which returns reproducible evidence for review; this split does not authorize automatic commit, push, tag, release, installation over the daily app, or production deployment.

- Development and daily use are separate channels. Local builds (including optimized builds) default to `app.todolist.desktop.dev` and its independent SQLite database; only explicit production builds use the existing `app.todolist.desktop` data. Desktop and MCP must share the same channel and path resolver. Never copy, clear, or migrate the existing user database as part of development setup.
- The global `todolist` MCP belongs to the installed app and daily tasks. This repository registers only `todolist_dev` for development tests; do not use it for daily tasks or silently fall back between the two servers. Development desktop builds cannot configure or remove the global integration. Keep a visible development window title and separate WebView storage.

- The selected visual source is `qa/source-reference.png`. Treat its left navigation, grouped task list, and right task detail as the desktop layout source of truth; the interaction-explanation column is documentation, not part of the app.
- TodoList is an independent local-first desktop app. Codex integration is optional and only reads, creates, or updates Todo data through MCP in the MVP.
- Do not add a Start Task or Send to Codex action in the MVP.
- A task may be pinned by the user into a compact always-on-top desktop note. Codex-created tasks must not open or pin that note automatically.
- Pinning is a compact task-row control: unpinned is gray, pinned is blue. Do not add a large pin action to the task detail footer.
- Subtasks can be completed independently. Completing all subtasks must not automatically complete the parent task.
- During the early product stage, prioritize core functionality and use Tauri's free updater-package signature for update integrity. Do not purchase or require Windows Authenticode signing yet; revisit public publisher signing only if adoption justifies it.
- Codex integration must be configured only after an explicit user action. Register the bundled MCP sidecar in the current user's `~/.codex/config.toml` and install the Skill under `~/.agents/skills/todolist-mcp`; never modify the Codex installation directory. Preserve conflicting or unowned entries instead of overwriting them.
- Local storage keeps one current workspace snapshot. Do not append duplicate full-workspace copies for audit or history; schema migrations must preserve user-facing task data and reclaim pages used only by obsolete internal storage.
- Desktop UI writes must reapply the user's explicit action to the latest persisted workspace after an MCP version conflict. Poll only the workspace version during idle periods and load the full snapshot only when that version changes.
- Search filters only the active Today, In Progress, or project view. Task editing applies explicit user field values onto the latest task while preserving fields outside the edit form.
- Acceptance criteria have independent persisted completion state, and a task cannot be completed while any criterion is unconfirmed. Archiving is reversible and clears pin state; permanent task deletion is available only from Archived with explicit confirmation. Deleting a project must list active and archived counts and let the user either move every task to an existing/new explicit destination or permanently delete the project and all its tasks after a second confirmation.
- Task detail is a fixed right-side overlay at every desktop width and must not resize, reflow, or reserve space in the main workspace. Keep the detail panel's scroll and footer visually independent from the workspace footer instead of presenting it as a third grid column. Opening and closing it must animate as a right-side slide; respect reduced-motion preferences.
- Because the floating detail can cover task-row controls, its title actions must include the same gray/blue pin toggle as the task row, placed immediately before Edit. Completion/reopen remains available in the detail footer.
- For Node/Vite previews, reuse an existing server only after confirming its workspace and command. Exclude high-churn generated directories such as Rust `target` from file watching, retain the owned process/session id, and stop that exact server after preview unless the user explicitly asks to keep it running. Never terminate unrelated Node processes in bulk.
- The sidebar has a separate Desktop Note entry that opens/reuses the sticky window and minimizes the main window only after the note is shown successfully. Task-row/detail pin toggles must not minimize the main window. An empty note can still be opened without pinning a task.
- The note's title region supports native dragging, including its text and icon, with a normal arrow cursor. Its close button must remain excluded from dragging. Windows release builds of the desktop GUI must not allocate a console window; the MCP sidecar retains STDIO behavior.
- A project color selected during project creation or editing must have visible feedback in the product UI; do not persist a color that is invisible everywhere.
- Keep the original six preset project colors, add a seventh named bright-red `#FF0000` preset, and offer the same compact custom-color control in project creation, editing, and new migration destinations. Custom colors use the native picker plus validated `#RGB`/`#RRGGBB` input, preserve existing custom values, and must not save while the input is invalid.
- After producing a new desktop build, always give the user a clickable absolute path to the newest `todolist-desktop.exe` so they can launch that exact build without searching build folders.
- Board card movement must use Pointer Events rather than native HTML `draggable`, which shows a forbidden-drop cursor in the Windows WebView. Start after a small movement threshold, ignore buttons and selects as drag handles, show a floating card preview and highlighted destination column, and keep the status selector as the keyboard-accessible fallback.
- The task-detail scrollbar must use the app's thin rounded blue-gray treatment instead of the platform's heavy default scrollbar.
- Detail and editor scrollbars stay hidden at rest, fade in while scrolling or when the pointer approaches the right scrollbar edge, then fade out after scrolling stops.
- Task detail shows the newest four activity entries by default and offers an inline `查看全部 / 收起` control for the retained history. Continue bounding persisted history to the newest 100 entries so activity data cannot grow indefinitely.
- Normal MCP task results omit activity history while retaining every other task field. Read one task's newest activity only through the separate read-only, version-bound paginated history tool, and call it only when the user explicitly asks to trace history.
- Keep the board's compact floating drag preview instead of moving a full-size card; preserving visible status columns and drop targets is more useful at the current four-column density.
- Codex launches the MCP sidecar independently of the desktop UI so tasks can be read or written while the task board is closed. The sidecar is not a user-facing executable, and MCP writes must not automatically open the task board.
- The sidebar includes an All view for every non-archived task, including unscheduled work. Search is visibly labeled and filters only the current task view.
- Clicking outside the floating task-detail panel closes it through the same slide-out transition as its close button; clicks inside the panel must not dismiss it.
- Codex integration records the last TodoList-managed MCP command beside the managed Skill. A changed install path is offered as a user-confirmed migration only when that recorded command matches, or for legacy installs when the managed marker exists and the old and current sidecar binaries are byte-identical. Migration changes only TodoList's command entry; unknown or unowned configurations remain conflicts.
- Task-detail attachments and images are separate persisted sections between description and subtasks. Originals are copied into the channel-specific managed directory and are never deleted by TodoList; removing a file, permanently deleting a task/project, or restoring a backup reclaims only unreferenced managed copies after the workspace save succeeds. Backups include referenced managed file content and restore it under new storage keys.
- The image browser uses at most three overlapping cards, separate non-wrapping previous/next controls, and a central large-image action. The viewer supports Escape, arrow keys, fit, original size and zoom without closing task detail. A single image has no previous/next controls.
- New desktop and ordinary browser workspaces start empty. Demo projects exist only behind the explicit browser `?demo=1` mode and neither desktop nor MCP initialization may seed them. Upgrades preserve existing SQLite, browser storage and managed files.
- Task-list multi-selection is separate from completion. Select-all is limited to the current view and search result; view/search changes reconcile selection. Normal lists batch archive, while Archived alone can batch permanently delete after confirmation. Batch mutations replay stable task ids on the latest workspace and never act on hidden or concurrently unarchived tasks.
- Windows installation stops only TodoList GUI and MCP processes whose resolved executable path is inside the selected installation directory. It must not close Codex or terminate same-named development/other-install processes. A transaction marker prevents Codex from restarting the new MCP during replacement, and installer failure rolls both components back together. Rollback must use the actual presence of owned backups, preserve originals that were never moved, survive interruption between a move and state persistence, and remain idempotent.
- Automatic-update installers are owned only after an explicit updater flag or a validated legacy Tauri temp layout plus an app marker. Successful installation verifies the GUI version and MCP build identity, then removes that attempt after the installer exits. Once both installed components are committed, later cache cleanup failure remains an installed result and is retried safely on startup; it must not trigger rollback or reinstall guidance. Failure retains the verified installer and opens Explorer once per actual retry; cancellation is recorded separately and does not open Explorer. Manual downloads, unmarked temp directories and unexpected files inside an owned cache are never reclaimed automatically.
- Automated installer acceptance must stay silent and must clean its unique fixture registration, shortcuts and temporary directory. The hook-level NSIS acceptance must exercise the real hooks with a nonzero installer PID, prove post-exit cache/helper cleanup, and redirect Explorer evidence to a test log rather than opening a window. Silent or passive automatic-update failure must not show a modal installer message; recovery remains available through the retained installer, the single required Explorer selection and the Settings recovery card.
- Every task view must keep its list scrollable within the workspace height, and each board status column must scroll vertically without moving its neighbors. Lists, board columns and narrow-screen horizontal board overflow reuse the task-detail auto-hiding thin blue-gray scrollbar treatment.
- Task descriptions preserve user-entered line breaks and wrap unbroken paths, URLs, English identifiers and Chinese text without changing stored content or creating horizontal detail overflow; long task titles must leave every title action reachable.
- Task detail opens as the normal fixed right overlay by default. Its leading title action lets the user temporarily expand the same fixed overlay across the app workspace and collapse it again without reflowing or resetting the covered view; closing and reopening detail returns to the normal width.
- The sidebar keeps task creation and primary navigation fixed at the top, and Desktop Note, Settings, integration state, and save state fixed at the bottom. Only the project list uses the remaining height for independent scrolling; its scrollbar stays permanently hidden while wheel, touchpad, and keyboard focus scrolling remain available. Keep the existing whole-project-group collapse behavior and do not apply this hidden-scrollbar rule to other app scroll regions.
- Workspace revision remains an internal conflict-control value and is not shown in the sidebar. The Settings row and update page use the real packaged software version; production desktop checks in the background with throttling, while browser/development previews never access the production updater endpoint and installation remains an explicit user action.
- List order is one shared `Workspace.tasks` order. Handle-only Pointer Event dragging and ArrowUp/ArrowDown reorder only the visible subset within one project and archived state, preserve hidden-task slots and every task field/version, append new tasks, and avoid persistence for no-op or cancelled movement.
- MCP `reorder_tasks` accepts the complete stable-id order for one project and archived state with the latest workspace version. It rejects stale, duplicate, missing, cross-project and cross-archive input atomically; versioned `list_tasks` cursors become stale after any intervening workspace change.
- A same-path managed Codex integration update is a neutral, explicit `更新集成` state rather than a repair failure. Explain whether the managed Skill or known complete legacy tool list changed, report the items actually updated, and ask the user to reconnect MCP or restart Codex. Compare complete tool lists as sets, preserve user-restricted tool permissions, keep path migration/missing/conflict/write errors distinct, and describe `configured` only as synchronized disk state rather than runtime connection health.
- The Today view includes every non-archived task with a valid real calendar due date on or before the local day, regardless of status or priority. Empty, whitespace-only, unscheduled-sentinel, and invalid legacy dates stay out of Today while remaining visible in All and project views; do not repair this by assigning or migrating user dates. UI and MCP date clearing normalize to the existing unscheduled sentinel, omitted MCP update fields preserve the current date, and nonempty invalid MCP dates are rejected before persistence.
- Production releases use GitHub Actions instead of routine local packaging. Pushes to `main` and pull requests run validation only; a production Windows build, updater signing and GitHub Release publication require an existing stable `vMAJOR.MINOR.PATCH` tag contained in `main` and matching the source version, either pushed normally or selected through the manual Release workflow. Signing secrets stay in GitHub Actions, verified assets are staged as a draft before publication, and published tags/releases are never overwritten. Keep the local DPAPI build path only as an explicitly requested maintainer fallback.
