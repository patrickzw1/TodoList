# Data backup and restore

TodoList exports one UTF-8 JSON file with `schemaVersion`, export time, app version and the current workspace. Schema version 2 contains projects, tasks, subtasks, acceptance criteria, dependencies, pin/archive state, attachment/image metadata, referenced managed-file content and the newest 100 activity entries per task. Version 1 backups remain importable and normalize missing attachment/image fields to empty lists.

Desktop builds use the operating system's native open/save dialogs. Export writes only the exact file selected by the user, rejects symlink or non-file targets, writes through a temporary file in the same directory and leaves neighboring files untouched. Import only reads the selected regular file and never modifies the source backup.

Both the TypeScript preview layer and the Rust desktop layer reject invalid JSON, files larger than 25 MB, unsupported schema versions, duplicate project/task ids and tasks that reference missing projects. Selecting a backup does not change data: the UI first shows its timestamp and project/task counts, and replacement requires a separate explicit confirmation.

The 25 MB limit applies to the whole JSON backup, including base64-encoded file content. A task can contain an individual file up to 100 MB, but a workspace with larger attachments may exceed this backup limit and cannot currently be exported as one JSON backup. Export failure leaves any previous backup intact. Desktop import also rejects missing, duplicate, unreferenced, or size-mismatched file payloads before replacing the workspace.

When confirmed, managed-file payloads are validated and written under new random storage keys before the imported workspace is reapplied to the latest persisted workspace version. Existing managed files are never overwritten. Successful workspace changes queue only files they removed for cleanup. Cleanup rechecks the latest workspace under the SQLite write lock, so a concurrent import or restore is not mistaken for an abandoned file. The queue survives restarts. The source backup and original imported files remain untouched. The version stored inside the backup is never used to overwrite the current database version, so the existing optimistic conflict handling remains active.
